# 09 版本差异与避坑清单

## 4.29.4 相对旧版的关键变化

以下均为源码核对结论，升级插件时优先检查这几项。

| 变化 | 旧版 | 4.29.4 | 影响 |
|---|---|---|---|
| Python 要求 | 3.10 / 3.11 可用 | **≥ 3.12** | 3.11 环境装不上 4.29.4；语法可用 3.12 特性 |
| `@register` 装饰器 | 需要装饰插件类 | **已废弃**（`[DEPRECATED]`），自动识别 `Star` 子类 | 保留不报错但无意义，新代码不要写 |
| 媒体模块路径 | `astrbot.core.utils.media_resolver` | **`astrbot.core.utils.media_utils`**（类仍叫 `MediaResolver`） | 引用旧路径的插件 `ImportError` |
| `MediaResolver` 方法 | 旧接口 | `as_path()` / `to_base64_data()` / `to_data_url()` / `to_path()` / `to_bytes()` | 按新名调整 |
| 配置注入 | 部分版本只传 `context` | `star_cls_type(context=..., config=AstrBotConfig)`，若 `TypeError` 回退只传 `context` | 建议 `__init__(self, context, config=None)` |
| `AstrBotConfig` | — | dict 子类，带 `save_config()` | 可直接 `cfg["KEY"]`、`cfg.get()` |
| 配置 schema 类型 | 文档写 9 种 | **10 种**（新增 `file`），仍**无 `number`** | 见 [02 章](02-配置Schema.md) |
| 图片预处理失败 | 直接报错/丢弃 | 判为「可恢复错误」，跳过图片并塞 `TextPart("[Image unavailable]")` | 补图插件必须清占位 |
| `on_llm_request` 时序 | — | `collect_initial_request` **之后**、`prepare_request_images` **之前** | 补图/改提示的正确位置 |
| 图片标准化 | — | `prepare_request_images` → `MediaResolver` 支持 `data:` / `file://` / 本地路径 | 插件塞本地路径或 data URI 都会被正确消费 |
| 引用图片兜底 | 无 | 内置 `core/utils/quoted_message/image_resolver.py`，多参数名 `get_image` + `get_file` 兜底 | 写图片插件应照抄该兜底顺序 |
| Agent 相关钩子 | 无 | 新增 `on_agent_begin` / `on_agent_done` / `on_using_llm_tool` / `on_llm_tool_respond` 等 | 更细的介入点 |
| 插件随附 Skills | — | `skills/` 目录自动纳入 Skill Manager | 新增能力 |
| 配置自动迁移 | — | 导入新版会迁移 `cmd_config.json`（补新增项、移除废弃项如 `provider_settings.llm_compress_keep_recent`） | 属 AstrBot 自身行为，仅影响本地配置文件 |

> 官方文档也提示：`docs.astrbot.app/dev/plugin.html` 已迁移到 `/dev/star/plugin.html`，而后者标注「v4.5.7 之后已过时」，当前应看 [`plugin-new.html`](https://docs.astrbot.app/dev/star/plugin-new.html)。网上大量教程停留在旧版，遇到冲突以源码为准。

## 避坑清单（逐条可核对）

### 加载阶段（插件根本起不来）

- [ ] `metadata.yaml` 在**根目录**，四个必填字段齐全且非空字符串。
- [ ] 入口是 `main.py`（或 `<目录名>.py`），类继承 `Star`。
- [ ] `_conf_schema.json` 的 `type` 全在 10 种白名单内，**没有 `number`**。
- [ ] `__init__` 调用了 `super().__init__(context)`，且不在构造函数里抛异常。
- [ ] `requirements.txt` 不与主环境冲突，依赖可安装。
- [ ] 没有残留 `__pycache__/`、`.git/` 被打进发布 zip。

### 运行阶段

- [ ] 处理函数是插件类的 `async def`，前两个参数 `self, event`。
- [ ] 用 `from astrbot.api.event import filter` 导入，没被内置 `filter` 覆盖。
- [ ] 用 `yield event.plain_result(...)` / `chain_result(...)`，不是 `print`。
- [ ] 日志用 `astrbot.api.logger` 或 `self.logger`，不是 `logging`。
- [ ] 网络请求用异步库，不用 `requests`。
- [ ] 数值配置读取后自己 `float()` / `int()` 归一化（面板可能存成字符串）。
- [ ] 遍历引用消息图片时覆盖了 `Reply.chain`。
- [ ] `event.bot` 取值前判断平台，调用 `call_action` 有 try/except。
- [ ] 持久化数据写到 `StarTools.get_data_dir()` 或 `data/` 下。

### 发布阶段

- [ ] 仓库 public，根目录直接是插件文件。
- [ ] `name` 与仓库名一致，`version` 已递增。
- [ ] zip ≤ 16 MB，含 `logo.png` 更佳。
- [ ] README 写明指令、配置项、依赖、灵感来源与许可证。

### 安装阶段

- [ ] 地址栏只填标准 `github.com` 地址，代理前缀填独立输入框。
- [ ] 国内网络优先用 zip 本地导入。
- [ ] 知道「未在仓库根目录找到 metadata.yaml」多为网络误报，不去瞎改仓库结构。

## 两个真实事故复盘

### 事故 A：`type: number` 让插件整体加载失败

日志：

```
[star.star_manager:1443] TypeError: 不受支持的配置类型 number。
支持的类型有：dict_keys(['int', 'float', 'bool', 'string', 'text', 'list', 'file', 'object', 'template_list', 'dict'])
```

根因：`_conf_schema.json` 里 `MAX_IMAGE_MB`、`CACHE_TTL_SEC` 写成 `"type": "number"`。4.29.4 的 `AstrBotConfig._config_schema_to_default_config()` 遇到白名单外的类型直接抛错，发生在 `star_manager.load()` 构造配置时，因此**整个插件加载失败**，不是某个配置失效。

修复：改 `float` / `int`；并加一个回归测试，用 `DEFAULT_VALUE_MAP` 校验所有 `type` + 真实构造一次 `AstrBotConfig(schema=...)`。注意这类问题**只测插件逻辑导入是测不出来的**，必须走加载路径。

### 事故 B：安装器报「未找到 metadata.yaml」但文件明明在

根因：安装器对 `raw.githubusercontent.com/.../HEAD/metadata.yaml` 的请求全部非 200（网络超时 / 代理异常 / 把代理前缀拼进地址栏导致改走 `git clone` 且克隆失败），代码里 `metadata is None` 就抛「未在仓库根目录找到」，**不区分文件不存在与网络失败**。

修复：不用改仓库结构。地址栏填标准地址、代理单独填、或直接用 zip 导入。
