AstrBot v4.29.4 插件开发指南

面向 AstrBot 4.29.4（Python ≥ 3.12）的插件创建指南与代码指南。 本指南所有 API、字段名、类型白名单、管线时序均从 4.29.4 实际安装源码逐项核对，而非照抄旧版文档或凭印象编写。 编写日期：2026-11-14。

这份指南解决什么

AstrBot 的官方文档分成了「旧版指南」「新版指南」「配置」「发布」等多个页面，且部分页面已标注过时；网上流传的插件教程多为 v3.x/v4.0 时代写法，直接套到 4.29.4 会出现「照着写却加载失败」的问题。本指南做三件事：

  1. 把 4.29.4 的真实约定固化下来：哪些字段必填、哪些类型合法、config 怎么注入、钩子何时触发。
  2. 给出可直接运行的代码：仓库 examples/ 下两个插件都在 AstrBot 4.29.4 / Python 3.12 环境里做过真实加载验证。
  3. 收录实测踩过的坑：配置类型写成 number 导致整个插件加载失败、安装器报「未在仓库根目录找到 metadata.yaml」其实是网络误报等，都给出根因和修复。

5 分钟：最小插件

目录放在 AstrBot 的 data/plugins/astrbot_plugin_hello/ 下：

astrbot_plugin_hello/
├── metadata.yaml      # 必需：插件身份
└── main.py            # 必需：入口（也可命名为与目录同名的 .py）

metadata.yaml（name/desc/version/author 四个字段必填且必须是非空字符串）：

name: astrbot_plugin_hello
desc: 一个最小示例插件
version: 1.0.0
author: YourName
repo: https://github.com/YourName/astrbot_plugin_hello

main.py：

from astrbot.api.event import AstrMessageEvent, filter
from astrbot.api.star import Context, Star
from astrbot.api import logger


class HelloPlugin(Star):
    def __init__(self, context: Context, config=None):
        super().__init__(context)          # 必须调用：注入 self.context / self.logger
        self.config = config or {}         # 4.29.4 传入的是 AstrBotConfig（dict 子类）

    @filter.command("hello")               # 发送 /hello 触发
    async def hello(self, event: AstrMessageEvent):
        """打招呼"""                       # docstring 会被解析为指令帮助
        yield event.plain_result(f"你好，{event.get_sender_name()}！")

    async def terminate(self):
        """插件卸载/停用时调用"""
        logger.info("[hello] 已卸载")

放进 data/plugins/ 后重启 AstrBot，或在 WebUI 插件页点「重载插件」。完整可运行版本见 examples/minimal/（见仓库对应文件）。

注意：@register(...) 装饰器在 4.29.4 已废弃，不要再用。加载器会自动识别所有继承 Star 的类（源码 core/star/base.py 的 __init_subclass__ + core/star/star_manager.py 的模块扫描）。

黄金法则（先记住这 8 条）

  1. 入口：main.py（或 <目录名>.py），类名任意，但必须继承 Star；处理函数必须写在插件类里，前两个参数是 self, event。
  2. 元数据：metadata.yaml 四个字段 name / desc / version / author 缺一不可，且都是非空字符串；文件名只能是 metadata.yaml 或 metadata.yml，必须在仓库根目录。
  3. 配置类型：_conf_schema.json 的 type 只接受 int / float / bool / string / text / list / file / object / template_list / dict。没有 number，写错会在加载阶段抛 TypeError，整个插件加载失败。
  4. 构造函数：写 def __init__(self, context: Context, config=None) 并调用 super().__init__(context)。加载器先尝试 config= 注入，若你的 __init__ 不接受则回退为只传 context。
  5. 日志：用 from astrbot.api import logger 或 self.logger，不要用 logging.getLogger；self.logger 是插件专属 logger，可在 WebUI 单独调级别。
  6. 返回结果：yield event.plain_result(...) / yield event.chain_result([...])，或 return 一个 MessageEventResult。处理函数是异步的。
  7. 网络请求：用 aiohttp / httpx 等异步库，不要用同步的 requests（会阻塞事件循环）。
  8. 持久化数据：写到 data/ 下（推荐 StarTools.get_data_dir()），不要写进插件自身目录 —— 插件更新/重装会覆盖。

适用范围说明

  • 本指南针对 AstrBot 4.29.4，对应 Python ≥ 3.12。旧版（如 4.14.6 及更早）部分 API 路径不同，见 09 版本差异。
  • 「AstrBot 泡泡版」等手机端打包发行版内置的就是 AstrBot 组件；插件目录、加载机制与桌面版一致，但不同运行环境的文件系统互不相通：在别处创建的 Linux 工作区 / Rootfs 里 mkdir 不出泡泡版的插件目录。
  • 官方资料：插件开发指南（新）、插件配置、发布到插件市场。本指南与官方文档冲突时，以 4.29.4 源码为准，并在文中标注差异。

01 项目结构与 metadata.yaml

插件放在哪

AstrBot 从两个位置扫描插件（源码 core/star/star_manager.py）：

  • data/plugins/ —— 用户插件（你要放的地方）
  • 内置保留插件目录（builtin_stars/）

插件是一个目录，目录名建议 astrbot_plugin_xxx（官方命名惯例：小写、无空格、尽量短、以 astrbot_plugin_ 开头）。

目录结构

astrbot_plugin_xxx/
├── main.py                 # 必需：入口
├── metadata.yaml           # 必需：身份信息（或 metadata.yml）
├── _conf_schema.json       # 可选：配置定义，有则自动生成配置文件并注入 __init__
├── requirements.txt        # 可选：pip 依赖
├── logo.png                # 可选：1:1，推荐 256×256，市场展示用
├── README.md               # 建议
├── skills/                 # 可选：随插件提供的 Skill（SKILL.md）
└── .astrbot-plugin/i18n/   # 可选：国际化 JSON

入口发现规则（源码 _get_modules）

加载器遍历 data/plugins/ 下的每个目录：

  1. 有 main.py → 导入 main 模块；
  2. 否则有 <目录名>.py → 导入同名模块；
  3. 两者都没有 → 跳过，并在日志里写 Plugin xxx has neither main.py nor xxx.py; skipping it.；
  4. 名字以 .plugin-install- / .plugin-upload- / .plugin-backup- 开头的目录被跳过（安装暂存与回滚备份）。

插件模块以包形式导入，因此支持相对导入（from .core.xxx import ...），但子目录要有 __init__.py 更稳妥。

类是怎么被发现的

不需要任何注册装饰器。Star.__init_subclass__（core/star/base.py）在类定义时把 StarMetadata 写入全局 star_map；star_manager.load() 扫描模块里所有继承 Star 的类并实例化。

@register(name=..., author=..., ...)（即 register_star）在 4.29.4 的源码里已明确标注 [DEPRECATED]，仅保留兼容。元数据以 metadata.yaml 为准。

metadata.yaml 字段

必填（4 个，且必须是非空字符串）

源码 core/star/updater.py：PLUGIN_METADATA_REQUIRED_FIELDS = ("name", "desc", "version", "author")。任一缺失或非字符串/空串 → 插件元数据校验失败 → 插件无法加载。

字段 说明
name 插件标识符，英文、唯一、小写、无空格。建议与仓库名一致
desc 详细描述，支持多行 / Markdown。可写成 description（会被规范化为 desc）
version 版本号，建议语义化版本（1.0.0）；带不带 v 前缀都可，市场按字符串比较递增
author 作者名

可选字段（4.29.4 实际读取的）

源码 star_manager._load_plugin_metadata()：

字段 类型 说明
display_name str WebUI / 市场展示名（v4.5.0+）
short_desc str 市场卡片短描述，缺省回退 desc
repo str 仓库地址。没有它无法在面板里更新插件
support_platforms list[str] 声明支持的适配器 ID，见下表
astrbot_version str 要求的 AstrBot 版本范围，PEP 440 格式，不要加 v，如 ">=4.16,<5"
views list 插件注册的页面元数据；pages 是兼容别名
i18n — 从 .astrbot-plugin/i18n/*.json 自动加载，不写在 yaml 里

tags、social_link 是插件市场读取的字段，AstrBot 本体的 _load_plugin_metadata 不解析，但发布到市场时建议填写。

astrbot_version 行为

不满足版本范围时，插件被阻止加载并提示版本不兼容；WebUI 安装时可勾选「无视警告，继续安装」跳过检查。格式遵循 PEP 440：>=4.17.0、>=4.16,<5、~=4.17。

安装器对 metadata 的额外要求

从 GitHub 地址 / zip 安装时（core/star/updater.py）：

  • 文件名只能是 metadata.yaml 或 metadata.yml；
  • 必须在仓库根目录（zip 则允许有一层顶层目录，安装器会自动识别）；
  • 必须是 UTF-8 编码（可带 BOM）；
  • 单个文件 ≤ 1 MB；
  • 必须是合法 YAML，且解析后是 dict，通过上面的必填字段校验。

安装器实际请求的是 https://raw.githubusercontent.com/{owner}/{repo}/HEAD/metadata.yaml（不带分支时用 HEAD），超时 15 秒。详见 08 排错。

requirements.txt

标准 pip 格式。4.29.4 在加载插件前会做依赖预检（_ensure_plugin_requirements → plan_missing_requirements_install），只安装缺失/版本不符的包；导入失败时还会尝试从已安装依赖恢复，再不行才重装。

aiohttp>=3.9
Pillow>=10.0

注意：不要在这里写 astrbot 本身；依赖冲突会在日志里报 Dependency conflict in plugin ...。

命名与体积红线（发布到市场时）

  • 仓库必须 public，根目录直接是插件文件（不要再套一层目录）；
  • 插件 zip ≤ 16 MB，超限 CI 直接拒绝；
  • name 与仓库名一致；
  • 不要提交 .git/、__pycache__/、node_modules/、data/。

02 配置 Schema（_conf_schema.json）

作用

在插件目录放 _conf_schema.json，AstrBot 会：

  1. 依据 schema 生成默认配置，保存为 data/config/<插件目录名>_config.json；
  2. 在 WebUI 插件配置弹窗里渲染可视化表单；
  3. 实例化插件时把配置对象作为 config 传给 __init__。

配置对象类型是 AstrBotConfig（astrbot.core.config.astrbot_config），继承自 dict，拥有字典全部方法，另有 save_config()。

致命陷阱：type 只能用这 10 种

源码 core/config/default.py 的 DEFAULT_VALUE_MAP 与 astrbot_config._config_schema_to_default_config()：

DEFAULT_VALUE_MAP = {
    "int": 0, "float": 0.0, "bool": False,
    "string": "", "text": "",
    "list": [], "file": [],
    "object": {}, "template_list": [], "dict": {},
}

只要 type 不在这个字典里，加载阶段立刻抛：

TypeError: 不受支持的配置类型 number。支持的类型有：dict_keys(['int', 'float', 'bool', 'string', 'text', 'list', 'file', 'object', 'template_list', 'dict'])

后果是整个插件加载失败（star_manager.load 里构造 AstrBotConfig 时抛错，插件进「加载失败」列表），不是一个配置项失效。

这是本指南收录的实测事故：把数值配置写成 "type": "number"（很多框架/JSON Schema 的写法），在 AstrBot 里非法。 数值请用 int（整数）或 float（可小数）。写 float 时 default 写 15 也没问题 —— _parse_schema 不校验默认值类型，只是直接赋值；插件里建议自行 float(...) / int(...) 归一化。

单行文本 / Token string ""

在插件里读配置

from astrbot.api.star import Context, Star


class MyPlugin(Star):
    def __init__(self, context: Context, config=None):
        super().__init__(context)
        self.config = config if isinstance(config, dict) else {}

    def _conf(self, key, default):
        """带兜底的读取：兼容 4.29.4 注入、旧版只传 context、以及直接实例化测试。"""
        if isinstance(self.config, dict) and key in self.config:
            return self.config[key]
        try:
            cfg = self.context.get_config()
            if isinstance(cfg, dict) and key in cfg:
                return cfg[key]
        except Exception:
            pass
        return default

    async def foo(self):
        enabled = self._conf("ENABLED", True)
        max_mb = float(self._conf("MAX_SIZE_MB", 15))   # 自己归一化类型
        retry = int(self._conf("RETRY_COUNT", 3))

要点：

  • 加载器（star_manager.load，约 1228 行）先尝试 star_cls_type(context=..., config=plugin_config)；若抛 TypeError（你的 __init__ 不接受 config），自动回退为只传 context。所以写 def __init__(self, context) 也不会崩，但拿不到配置。
  • 建议始终把 config 存到 self.config，并用 _conf() 兜底 —— 面板里用户删了配置项、配置迁移、单元测试直接实例化时都不会 KeyError。
  • 修改后可调用 self.config.save_config() 持久化（注意并发与用户面板编辑的覆盖关系）。
  • 发布新版本更新 schema 时，AstrBot 会递归补齐缺失项、移除已不存在的项。

回归测试：锁死类型合法性

把这段放进插件的测试里，可以在升级 AstrBot 或改 schema 时立刻发现问题：

import json, pathlib
from astrbot.core.config.default import DEFAULT_VALUE_MAP
from astrbot.core.config.astrbot_config import AstrBotConfig

schema = json.loads(pathlib.Path("_conf_schema.json").read_text(encoding="utf-8-sig"))
bad = {k: v.get("type") for k, v in schema.items() if v.get("type") not in DEFAULT_VALUE_MAP}
assert not bad, f"存在不支持的配置类型: {bad}"

cfg = AstrBotConfig(config_path="/tmp/test_config.json", schema=schema)
assert cfg["ENABLED"] is True

03 Star 类与生命周期

继承与实例化

所有插件继承 Star（astrbot.api.star.Star → astrbot.core.star.base.Star）。Star 同时混入 CommandParserMixin 和 PluginKVStoreMixin。

源码 star_manager.load() 的实例化逻辑（约 1222–1240 行）：

# 注入类属性，便于 __init__ 读取
setattr(star_cls_type, "name", p_name)
setattr(star_cls_type, "author", p_author)
setattr(star_cls_type, "plugin_id", plugin_id)

if plugin_config and star_cls_type:
    try:
        star_cls = star_cls_type(context=self.context, config=plugin_config)
    except TypeError:
        star_cls = star_cls_type(context=self.context)   # 回退
elif star_cls_type:
    star_cls = star_cls_type(context=self.context)

三个推论：

  1. config 是关键字参数，类型 AstrBotConfig（dict 子类）；有 _conf_schema.json 才非空。
  2. 写 def __init__(self, context) 也能加载（走回退），但读不到配置。
  3. 类名任意、不需要 @register；Star.__init_subclass__ 自动登记到 star_map。

标准构造函数

from astrbot.api.star import Context, Star


class MyPlugin(Star):
    def __init__(self, context: Context, config=None):
        super().__init__(context)      # 必须！否则没有 self.context / self.logger
        self.config = config if isinstance(config, dict) else {}
        # 其他初始化：读配置、建缓存、创建后台任务等

super().__init__(context) 做两件事（core/star/base.py）：

  • self.context = context
  • 从 star_map 解析插件名，绑定插件专属 logger 到 self.logger（astrbot.plugin.<plugin_name>，级别可在 WebUI 单独设置）

若插件类把 logger 定义成只读 property，Star.__init__ 会捕获 AttributeError 并保留你自己的实现。

指令

基础

@filter.command("hello")
async def hello(self, event: AstrMessageEvent):
    """打招呼"""                 # docstring 会解析成指令帮助
    yield event.plain_result("Hello!")
  • 指令不能带空格（空格会被解析成参数）。

所有注册函数都收 **kwargs，其中 priority 存进 StarHandlerMetadata.extras_configs，默认 0。

   ↓
⑤ prepare_request_images()
   - 用 MediaResolver / prepare_model_image 逐项标准化 req.image_urls
   - 支持本地路径、file:// URI、data: base64 URI
   ↓
⑥ 调用 LLM
   ↓
on_llm_response → on_decorating_result → 发送

关键结论 1：AstrBot 没有「预处理之前」的插件钩子。预处理永远先于插件，因此 gchat.qpic.cn 400 这类 WARNING 无法被任何插件消除（它无害，可忽略）。

关键结论 2：on_llm_request 在 ③ 之后、⑤ 之前。插件此时能同时看到「原始消息段（仍带 file_id）」和「已构造好的 req」，是修复图片、改系统提示的唯一正确位置。

4.29.4 图片管线细节（写给要修图片的人）

① 预处理阶段的失败判定

is_recoverable_image_error()（core/utils/media_utils.py）把 DownloadFileHTTPError（HTTP 400/403/404 等）判为可恢复错误：不中断消息处理，只跳过该图片。因此 QQ 图片因 rkey 失效返回 400 时，插件仍有机会介入。

② [Image unavailable] 占位文本

collect_initial_request()（core/astr_main_agent.py 约 1540–1630 行）对下载失败的图片插入：

TextPart(text="[Image unavailable]")

到 req.extra_user_content_parts。插件补回图片后必须等量清除这句，否则 LLM 会同时收到「图不可用」和实际图片，自相矛盾。

③ 图片标准化

prepare_request_images() → prepare_model_image(ref, max_size, output_dir)：

  • 内部用 MediaResolver（core/utils/media_utils.py）解析引用；
  • 支持本地路径、file:// URI、data:image/png;base64,...；
  • describe_media_ref() 生成给 LLM 的描述，不会把 base64 payload 泄漏进提示文本；
  • max_size 必须 > 0（如 1568），传 0 会返回 None。

模块路径变化：旧版 astrbot.core.utils.media_resolver → 4.29.4 为 astrbot.core.utils.media_utils（类仍叫 MediaResolver，方法 as_path() / to_base64_data() / to_data_url() / to_path() / to_bytes()）。引用该内部模块的旧插件需要改名。

④ 官方自带的取图兜底可作为参考

4.29.4 内置 core/utils/quoted_message/image_resolver.py，用 get_image 的 file / file_id / id / image 四种参数名 + get_file 兜底解析引用消息图片。写图片修复插件时应照抄这个兜底顺序，只试一种参数名命中率很低。

完整案例：图片本地化修复插件骨架

针对「QQ/NapCat 因 rkey 失效导致 gchat.qpic.cn 图片 400、机器人看不到图」的场景，插件思路是：用 OneBot get_image 取协议端本地缓存，绕开腾讯 CDN 与 rkey。

import base64
from astrbot.api.event import AstrMessageEvent, filter
from astrbot.api.message_components import Image, Reply
from astrbot.api.provider import ProviderRequest
from astrbot.api.star import Context, Star
from astrbot.api import logger

UNAVAILABLE = "[Image unavailable]"


class ImageFixPlugin(Star):
    def __init__(self, context: Context, config=None):
        super().__init__(context)
        self.config = config or {}

    @filter.on_llm_request()
    async def fix(self, event: AstrMessageEvent, req: ProviderRequest):
        # 1) 收集预处理失败的图片 file_id（顶层 + 引用链）
        ids = []
        for comp in event.message_obj.message or []:
            if isinstance(comp, Reply) and comp.chain:
                items = comp.chain
            else:
                items = [comp]
            for seg in items:
                if isinstance(seg, Image) and seg.file:
                    ids.append(seg.file)

        # 2) 逐个用 get_image 多参数名兜底取本地缓存
        added = 0
        for fid in dict.fromkeys(ids):
            data = await self._fetch(event, fid)
            if not data:
                continue
            uri = "data:image/jpeg;base64," + base64.b64encode(data).decode()
            if uri not in req.image_urls:
                req.image_urls.append(uri)
                added += 1

        # 3) 等量清除占位文本
        if added:
            parts = req.extra_user_content_parts
            removed = 0
            keep = []
            for p in parts:
                txt = getattr(p, "text", None)
                if removed < added and txt and txt.strip() == UNAVAILABLE:
                    removed += 1
                    continue
                keep.append(p)
            req.extra_user_content_parts = keep
            logger.info("[imagefix] 补图 %d 张，清除占位 %d 条", added, removed)

    async def _fetch(self, event, fid):
        bot = getattr(event, "bot", None)
        if bot is None:
            return None
        for action in ("get_image", "get_file"):
            for key in ("file", "file_id", "id", "image"):
                try:
                    ret = await bot.api.call_action(action, **{key: fid})
                    # 返回可能是路径 / base64 / dict，需归一化后读取字节
                    ...
                except Exception:
                    continue
        return None

要点与局限：

  • 不要改写消息组件本身（改 Image.url 无效，预处理已跑完），只需写 req.image_urls。
  • 图片已成功时 url 会被改写成本地路径，插件应跳过，避免重复。
  • data: URI 与本地路径都能被 ⑤ 的 MediaResolver 消费，不会二次下载。
  • 该插件治标：预处理 400 警告与群文件 retcode=1400 packetBackend 不可用 属于另一条链路，插件消除不了；彻底解决要对齐 QQ 版本与协议端支持的版本映射，或换协议端。

本仓库的实现参考：astrbot_plugin_qpicfix（v1.1.1，已在 4.29.4 做过 8 项集成测试）。

以下均为源码核对结论，升级插件时优先检查这几项。

变化 旧版 4.29.4 影响
Python 要求 3.10 / 3.11 可用 ≥ 3.12 3.11 环境装不上 4.29.4；语法可用 3.12 特性
@register 装饰器 需要装饰插件类 已废弃（[DEPRECATED]），自动识别 Star 子类 保留不报错但无意义，新代码不要写
媒体模块路径 astrbot.core.utils.media_resolver astrbot.core.utils.media_utils（类仍叫 MediaResolver） 引用旧路径的插件 ImportError
MediaResolver 方法 旧接口 as_path() / to_base64_data() / to_data_url() / to_path() / to_bytes() 按新名调整
配置注入 部分版本只传 context star_cls_type(context=..., config=AstrBotConfig)，若 TypeError 回退只传 context 建议 __init__(self, context, config=None)
AstrBotConfig — dict 子类，带 save_config() 可直接 cfg["KEY"]、cfg.get()
配置 schema 类型 文档写 9 种 10 种（新增 file），仍无 number 见 02 章
图片预处理失败 直接报错/丢弃 判为「可恢复错误」，跳过图片并塞 TextPart("[Image unavailable]") 补图插件必须清占位
on_llm_request 时序 — collect_initial_request 之后、prepare_request_images 之前 补图/改提示的正确位置
图片标准化 — prepare_request_images → MediaResolver 支持 data: / file:// / 本地路径 插件塞本地路径或 data URI 都会被正确消费
引用图片兜底 无 内置 core/utils/quoted_message/image_resolver.py，多参数名 get_image + get_file 兜底 写图片插件应照抄该兜底顺序
Agent 相关钩子 无 新增 on_agent_begin / on_agent_done / on_using_llm_tool / on_llm_tool_respond 等 更细的介入点
插件随附 Skills — skills/ 目录自动纳入 Skill Manager 新增能力
配置自动迁移 — 导入新版会迁移 cmd_config.json（补新增项、移除废弃项如 provider_settings.llm_compress_keep_recent） 属 AstrBot 自身行为，仅影响本地配置文件

官方文档也提示：docs.astrbot.app/dev/plugin.html 已迁移到 /dev/star/plugin.html，而后者标注「v4.5.7 之后已过时」，当前应看 plugin-new.html。网上大量教程停留在旧版，遇到冲突以源码为准。

避坑清单（逐条可核对）

加载阶段（插件根本起不来）

  • [ ] metadata.yaml 在根目录，四个必填字段齐全且非空字符串。
  • [ ] 入口是 main.py（或 <目录名>.py），类继承 Star。
  • [ ] _conf_schema.json 的 type 全在 10 种白名单内，没有 number。
  • [ ] __init__ 调用了 super().__init__(context)，且不在构造函数里抛异常。
  • [ ] requirements.txt 不与主环境冲突，依赖可安装。
  • [ ] 没有残留 __pycache__/、.git/ 被打进发布 zip。

运行阶段

  • [ ] 处理函数是插件类的 async def，前两个参数 self, event。
  • [ ] 用 from astrbot.api.event import filter 导入，没被内置 filter 覆盖。
  • [ ] 用 yield event.plain_result(...) / chain_result(...)，不是 print。
  • [ ] 日志用 astrbot.api.logger 或 self.logger，不是 logging。
  • [ ] 网络请求用异步库，不用 requests。
  • [ ] 数值配置读取后自己 float() / int() 归一化（面板可能存成字符串）。
  • [ ] 遍历引用消息图片时覆盖了 Reply.chain。
  • [ ] event.bot 取值前判断平台，调用 call_action 有 try/except。
  • [ ] 持久化数据写到 StarTools.get_data_dir() 或 data/ 下。

发布阶段

  • [ ] 仓库 public，根目录直接是插件文件。
  • [ ] name 与仓库名一致，version 已递增。
  • [ ] zip ≤ 16 MB，含 logo.png 更佳。
  • [ ] README 写明指令、配置项、依赖、灵感来源与许可证。

安装阶段

  • [ ] 地址栏只填标准 github.com 地址，代理前缀填独立输入框。
  • [ ] 国内网络优先用 zip 本地导入。
  • [ ] 知道「未在仓库根目录找到 metadata.yaml」多为网络误报，不去瞎改仓库结构。

两个真实事故复盘

事故 A：type: number 让插件整体加载失败

日志：

[star.star_manager:1443] TypeError: 不受支持的配置类型 number。
支持的类型有：dict_keys(['int', 'float', 'bool', 'string', 'text', 'list', 'file', 'object', 'template_list', 'dict'])

根因：_conf_schema.json 里 MAX_IMAGE_MB、CACHE_TTL_SEC 写成 "type": "number"。4.29.4 的 AstrBotConfig._config_schema_to_default_config() 遇到白名单外的类型直接抛错，发生在 star_manager.load() 构造配置时，因此整个插件加载失败，不是某个配置失效。

修复：改 float / int；并加一个回归测试，用 DEFAULT_VALUE_MAP 校验所有 type + 真实构造一次 AstrBotConfig(schema=...)。注意这类问题只测插件逻辑导入是测不出来的，必须走加载路径。

事故 B：安装器报「未找到 metadata.yaml」但文件明明在

根因：安装器对 raw.githubusercontent.com/.../HEAD/metadata.yaml 的请求全部非 200（网络超时 / 代理异常 / 把代理前缀拼进地址栏导致改走 git clone 且克隆失败），代码里 metadata is None 就抛「未在仓库根目录找到」，不区分文件不存在与网络失败。

修复：不用改仓库结构。地址栏填标准地址、代理单独填、或直接用 zip 导入。
